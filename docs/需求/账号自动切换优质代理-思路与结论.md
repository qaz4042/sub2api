# 账号自动切换优质代理：思路与结论

本文按本地提交 `8ed099f39` 的实现整理。完整设计见 [账号自动切换优质代理](./账号自动切换优质代理.md)，决策流程见 [Mermaid 流程图](./账号自动切换优质代理-流程.mermaid)。本次整理未核查线上是否已部署该提交。

## 目标与范围

- 为显式开启的独立 OpenAI 账号自动选择合适的代理，不定时轮换 IP。
- 默认关闭；新配置默认使用全部符合条件的代理，也可指定 2–10 个候选并包含当前代理。已有指定池配置不会自动扩大。
- 全部模式会动态纳入新增合格代理。系统不自动约束出口地区、供应商或容量，管理员须确认候选适合账号。
- 不接管直连账号、影子账号或处于固定主备回退状态的账号。手工改绑后暂停托管；关闭功能保留当前绑定。

## 为什么采用监测延迟

实际请求的模型、输入和上游负载不同，首字耗时难以公平比较；要求每个账号先在候选代理上积累业务历史，也会使主动择优长期没有候选。因此，**正常择优使用代理 OpenAI 连通监测的 P95 延迟，实际请求继续用于识别故障**。

探测的 200/401 只说明连通，不代表账号鉴权、模型调用成功或实际推理更快。鉴权、限额、客户端取消及无法归因的失败不作为代理传输故障。

## 切换规则

| 场景 | 判断与处理 |
| --- | --- |
| 监测资格 | 代理启用、未过期、监测开启且非固定主备；近 5 分钟监测新鲜、覆盖充分、成功率至少 80%、最近 3 次成功，且有 P95 延迟。主动择优时当前代理和候选均需满足。 |
| 正常择优 | 目标每 30 秒评估一次；候选 P95 相比当前代理同时改善至少 30% 和 200ms，选择 P95 最低的合格候选。 |
| 连续确认 | 同一候选连续 3 次评估达标，且每次确认前当前代理和候选各有新完成探测，才切换。进度持久化；候选、连接指纹或配置变化，或监测不再合格时重置。 |
| 传输故障 | 当前代理失效、发生持久传输错误、近 5 分钟同模型同入口连续 3 次传输失败，或至少 5 个已识别请求的成功率低于 80% 时，可走故障切换。监测合格但没有该账号历史的候选也可接管。 |
| 5xx | 同模型、同入口连续 3 次 5xx 时，候选还须有相同业务维度的历史：近 1 小时至少 5 个已识别请求且成功率至少 80%，近 5 分钟至少 2 次成功，最近成功晚于该组首个 5xx。缺少证据时暂停监测择优并清空确认进度；明确传输故障仍可走故障路径。 |
| 冷却 | 正常切换后冷却 5 分钟；确认故障可在 1 分钟后再次切换。 |
| 无法判断 | 采集有缺口、监测不足、没有合格候选或其他保护条件不满足时保持当前绑定，等待后续评估。 |

故障切换优先使用具有合格业务历史的候选；没有此类候选时，传输故障可按监测 P95 选择冷启动候选。实际请求的成功率只计已识别的成功和传输失败；5xx 单独处理。

## 保护与边界

- 账号配置、候选检查和切换在事务中协调；切换审计、账号绑定和调度通知一起提交，多实例不会重复执行同一轮。
- 采集缺口会暂停切换；切换前会复核采集状态。调度快照按既有机制更新，已开始的请求和长连接不强制断开。
- 三次评估使用重叠的 5 分钟窗口，虽然要求新探测，仍可能受同一次延迟尖峰影响。
- 当前没有针对鉴权或地区问题的自动回退、失败候选隔离，也不主动发起账号业务试用。监测合格的代理仍可能不适合某个账号。
- 页面展示监测合格备选数、最近评估和最近 20 条切换记录；合格备选数不等于一定会切换。

## 已确认的现场情况

2026-10-30 对 my4g 的只读核查显示，三个账号曾因监测冷启动切到 `新加坡SG-HY2`。当时该代理的探测 P95 明显高于部分候选，但原策略要求候选具有同账号业务历史，因此没有基于监测延迟主动择优。上述提交已在本地实现监测延迟择优与 5xx 保护；现场数据是核查时的快照，不代表当前状态。
