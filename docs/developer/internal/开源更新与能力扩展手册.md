# 开源更新与能力扩展手册

## 目标

在持续吸收 `Wei-Shaw/sub2api` 上游更新的同时，保留本站产品、运营和部署差异。原则是：**上游核心保持可更新，定制能力独立实现，只通过少量接入点连接。**

目标不是零冲突，而是避免在 gateway、settings、routes、router、菜单和语言包等热点文件反复产生大段冲突。

## 归属判断

| 需求 | 处理方式 |
| --- | --- |
| 通用修复、协议兼容、安全与稳定性改进 | 拆成独立提交，优先贡献上游。 |
| 支付、风控、私有登录、品牌、运营或部署差异 | 放定制扩展目录。 |
| 必须进入主流程 | 先补最小 contract、registry 或 slot；私有实现不散落进核心文件。 |

不复制完整 `handler`、`service`、`views/admin` 或基础组件目录；不长期堆叠 `if privateXxx`；不修改历史 migration。

## 目录与接入

### 前端

```text
frontend/src/
  components/、views/、api/       # 上游通用实现
  extensions/private/<feature>/   # 私有页面、组件、API、状态、语言包、测试
  registries/                     # 菜单、路由、设置、页面扩展等少量入口
```

私有功能应拥有自己的组件、弹窗、状态、API、语言包和测试。公共页面只负责一次性接入：新增按钮和弹窗优先使用命名 slot 或 action/dialog registry；不在公共页面增加私有 `showXxx`、`selectedXxx`、`handleXxx`。

### 后端

```text
backend/internal/
  handler/、service/、repository/       # 上游核心流程
  contracts/                            # 稳定扩展接口
  extensions/private/<feature>/         # 私有 routes、handler、service、repository、测试
  server/extension_registry.go          # 集中装配扩展
```

网关风控使用 policy 或 middleware；支付使用 provider；私有登录和管理 API 使用 route registrar；运营配置使用 config provider。核心文件只负责调用契约或注册扩展。

### 其他资产

| 范围 | 约定 |
| --- | --- |
| 迁移 | 只追加；私有迁移有独立命名和注册约定。 |
| 配置 | 私有变量以 `PRIVATE_` 为前缀，由私有配置模块读取。 |
| 部署、CI | 放 `deploy/private/`、`private-*.yml`，以覆盖或额外入口接入。 |
| 文档、品牌 | 放私有目录或既有 `docs/platform/`，不替换上游默认资产。 |
| 测试 | 跟随私有模块；公共接入点保留最小契约测试。 |

## 分支与提交

```text
upstream/main -> main -> codex/migrate-openai-privacy -> origin/codex/migrate-openai-privacy
                 上游镜像              部署主干                       远端部署主干
```

- `main` 跟踪 `upstream/main`，保持纯净，不合入私有部署改动。
- `codex/migrate-openai-privacy` 是部署主干，只接受 `main` 向它合并，不反向污染 `main`。
- 功能从部署主干创建；提交保持单一意图，不能混入文案、部署、格式化和无关重构。
- 已推送或已部署的主干使用 merge 持续同步，不 rebase、不强推。

## 一项能力的闭环

1. 归类：上游候选或私有扩展。
2. 查找接入点；缺失时仅增加一个最小 contract、registry 或 slot。
3. 在独立 feature 完成业务、配置和测试。
4. 只修改一个公共接入点。
5. 验证关闭配置后的默认行为、权限和错误路径。
6. 单独提交并注明接入点；可复用部分准备贡献上游。

既有深度耦合代码不做一次性重构。以后修改该能力时，再将新增逻辑迁出热点文件并补契约测试。

## 日常上游更新

保持“小步、定期、可回滚”：先更新纯净 `main`，再把 `main` 合入部署主干。不要直接在部署主干拉取未知远端，也不要把部署主干合回上游基线。

```bash
# 1. 同步所有远端引用
git fetch --all --prune

# 2. 更新纯净上游基线
git switch main
git merge --ff-only upstream/main

# 3. 合入部署主干
git switch codex/migrate-openai-privacy
git status --short --branch
git merge --no-ff main
```

大版本更新前可先创建并推送备份分支。发生冲突时，先查看全部未解决文件：

```bash
git diff --name-only --diff-filter=U
```

冲突处理顺序：保留上游核心与安全修复 → 让私有模块适配新 DTO、路由和契约 → 同一位置的独立能力同时保留 → 重新生成 Ent/Wire 等生成代码。不要用整文件 `ours/theirs` 覆盖热点文件，也不要在冲突处重新塞回散落的私有判断。

冲突清零后重点检查跨分支组合，而不只检查编译：

- composite 路由解析后的目标平台，必须与平台启停中间件一致，不能把 `composite` 当作未配置平台误拒绝。
- 新增 alias、模型列表、count-tokens、图片和实时接口时，核对鉴权、分组、平台开关和 body limit 是否完整。
- 上游新增 API 或 interface 方法后，补齐私有测试中的 mock/stub；关键测试通过之外，定期运行完整 Vitest。
- migration 只追加；编号可重复但文件名必须唯一，并确认完整文件名排序不会破坏依赖顺序。

按改动执行最小充分验证：

- gateway、计费、认证、迁移：相关 Go 测试。
- 页面、路由、菜单、弹窗：相关 Vitest 与 `pnpm --dir frontend run typecheck`。
- 构建、嵌入式前端：对应 build。
- 配置、部署：静态校验与文档核对；除非明确批准，不部署。

常规合并至少执行：

```bash
(cd backend && go test ./...)
make test-frontend
git diff --check
git diff --cached --check
```

高风险或准备发布时再执行完整前端测试和构建。确认结果后完成 merge commit；先审查，再推送，推送不等于部署：

```bash
git commit                         # 仅在冲突解决后需要
git push origin codex/migrate-openai-privacy
```

若验证失败，保持本地 merge 不推送；修复应作为小提交，避免修改已发布的历史 migration。尚未提交且确认要放弃整个合并时，才使用 `git merge --abort`。

## 每周检查

- [ ] 评估上游安全、稳定性、迁移和公共 API 更新。
- [ ] 拆分可回馈的通用修复。
- [ ] 检查私有功能是否仍只修改约定接入点。
- [ ] 确认私有迁移、配置、部署模板和回滚说明一致。
- [ ] 发布前验证定制关闭时仍保持上游默认行为。
